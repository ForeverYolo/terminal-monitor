## 一、当前问题

### 现象

1. 打开 monitor 终端，**有概率什么都不显示**，重进才可能恢复
2. 可翻的历史**只有十几行**（monitor-3）或**翻到某条就断**（monitor-1，例如只到
   `● Update(~/ComRAG-medical/scripts/screen_dense_vs_lexical.py)` 那条附近）
3. 不同终端程度不同：Claude 活跃跑任务的终端（monitor-3）最严重

### 排查过程（已逐一排除的嫌疑）

| 嫌疑 | 排除证据 |
|---|---|
| 服务器没发历史 | 探针实测：monitor-3 缓冲 13402 帧，回放正常发出 3000 帧 / 375KB |
| 浏览器过滤器吃数据 | 抓真实回放流灌入 `createAltScreenFilter`：92% 字节保留，正常 |
| 光标隐藏改写（`b71a8ec`） | 该改动只做 `ESC[?25l → ESC[?25h` 的 6 字节替换，不改位置语义；且上线两天内历史一直正常 |
| 双清屏回归（已修） | 回放收尾的 `scrollback_info` 重复携带 `mode:'full'`，浏览器在数据画完后二次清屏 → `0c5f782` 已修；修掉了"概率空白"，但"历史短/断"仍在 |

### 根因（用 headless xterm 实测确认）

把线上真实回放流灌进 headless xterm 渲染：

- monitor-1：911 行（服务器发了 3000 帧 / 31.8 万字节，正常密度应为数千行）
- monitor-3：334 行，视口是错位碎片（表格残片互相重叠）
- 统计流内容：monitor-3 的窗口里 **绝对定位序列（ESC[H）0 条**，相对移动
  （`ESC[8A` 等）1300+ 条/千帧；monitor-1 有 20 条绝对定位

结论：**服务器缓冲里存的是"画画动作的录像"（字节流增量），不是"画完成品"**。
相对移动指令的语义依赖"执行时光标在哪"这个隐含状态，而这个状态只存在于
screen 的内存里、从不在字节流中。回放把录像从中间一段开始放给一张白纸：

```
帧意图（screen 端）:  光标在15行 → 上移3行 → ✶ 画在12行
回放执行（空 xterm）: 光标在0行  → 上移3行 → ✶ 画在0行（错位）
```

错位帧里的擦除（`ESC[K`）/覆盖写入跟着落在错误的行上，把前面画对的内容
擦掉、盖掉。两种帧混合污染：自包含的"打印行+滚动"帧画出正确内容，随后的
错位重绘帧毁掉一部分，净效果就是"能翻的内容断断续续、只有十几行"。

### 为什么"以前一直可以"

旧架构 scrollback 挂在每次连接上，client 重连（agentId 换新）缓冲即清零；
重连时 client 重新 attach screen，**附着瞬间 screen 整屏重绘**（绝对坐标），
所以回放窗口的起点几乎总是自包含的。`8fe7146` 把缓冲挪到稳定键上、跨重连
保留（修手机端 monitor-2 不刷新的目标达成了），副作用是窗口起点变成任意
时刻——自包含起点没了，这个潜伏缺陷就暴露了。

## 二、方案

### 设计原则

历史（可翻）和实时（当前视口）**用不同来源，各取所长**：

```
可翻历史   ← screen 自己的缓冲（成品文本，100% 正确，不依赖光标状态）
实时/接续  ← 现有字节流 + seq（颜色齐全）
两者焊接点 ← 整屏重绘（绝对坐标，自声明状态，不依赖任何前文）
```

核心洞察：链路里唯一自包含的东西是**整屏重绘**——绝对坐标帧
（`ESC[12;5H✶`）本身就是状态陈述，不需要参照系。screen 察觉 PTY 尺寸变化
即会整屏重绘（现有 `scrollback_end` 的 resize nudge 已在用这个技巧）。

### 回放流程（目标态）

```
浏览器打开终端
  ① 服务器让 agent 执行 screen -S <name> -X hardcopy -h /tmp/xx.txt
     读回文件 → 全量成品文本历史（黑白，丢颜色）
  ② 浏览器清屏，写入这份文本（可翻历史就位）
  ③ resize nudge → screen 整屏重绘（绝对坐标+彩色）
     把"当前视口 + 精确光标位置"覆盖到 xterm 上
  ④ 实时帧（相对移动）照旧 → 参照系已被③精确建立，无缝续上
```

- 锚点取 **client 读回文件的时刻**：缺口（导出→写入之间产生的输出）压缩到
  近似为零，且缺口内容落在③的重绘视口内，被覆盖补上
- ①③ 内容重叠且一致（同一时刻同一屏幕），是重叠覆盖，不是断层
- 不再做全量字节流回放；字节流缓冲降级为"几秒接续 + 实时"的用途

### 剩余损耗（第一版）

①导出截止后、②重绘视口外滚过的行（约 1 秒窗口内的开头一两行）可能缺。
量级是"行"不是"屏"，且对 4 万行会话无感。

### 无损升级路径（第二版，可选）

client 侧（与 screen 同机）跑一个轻量渲染器：转发字节流的同时喂给
headless 终端模拟器，维护"当前屏幕"，**行滚出视口时把带 SGR 的成品行存进
环形缓冲**（~5000 行）。回放变成：

```
hardcopy 早期历史（黑白）
  + 环形缓冲近 5000 行（彩色、无损）
  + 整屏重绘（视口+光标）
```

渲染器无起点问题：client 启动时先做一次 hardcopy 给它打底（或 resize
nudge 拿绝对坐标帧建立状态），client 重启自动校准，错误不累积。

第一版上线后若"近几千行颜色丢失"影响体验，再做第二版。

### 改动面

| 文件 | 改动 |
|---|---|
| client.js | 新增 hardcopy 导出处理器：收到请求 → `screen -X hardcopy -h` → 读回文件 → 上报（含锚点时刻） |
| server.js | 新增 history 请求中转；回放流程改为"hardcopy 文本 + 整屏重绘锚"，去掉全量字节流回放 |
| public/index.html | 收到 history 消息：清屏→写文本→（服务器随后 nudge 重绘）；seq 接续逻辑不变 |

### 回答过的关键质疑（设计决策记录）

- **"为什么不直接上报磁盘态给徽章"式的直接方案（用服务器缓冲当历史）？**
  服务器存的是录像不是成品，缺光标隐含状态，数学上不可能重建（除非存成品）。
- **"导出后新数据来了怎么办 / 光标位置怎么知道？"**
  锚点取读回时刻；resize nudge 强制整屏重绘，screen 用绝对坐标自声明光标
  与视口，无猜测环节。
- **"重绘会不会和前面历史断层？"**
  ①②画的是同一时刻同一屏幕，重叠区一致；是覆盖不是拼接。
- **"有没有无损方法？"**
  第一版（hardcopy+重绘锚）唯一损耗是 1 秒窗口内可能缺开头一两行；
  第二版（client 渲染器+环形缓冲）完全无损。

### 测试计划

1. `test-history-replay.js`：raw agent socket 模拟 screen（hardcopy 文件），
   全流程断言：①文本到达 ②nudge 重绘 ③seq 接续 ④实时帧正常
2. headless xterm 渲染断言：回放后缓冲行数与 hardcopy 行数一致（不再出现
   "3000 帧只画出 334 行"）
3. 回归：现有 85 条断言全绿（尤其 test-stable-resume 的 seq/tail 语义）

### 顺带收益

- 服务器重启不再丢可翻历史（历史源头在 screen，不依赖服务器内存）
- 2MB 字节流缓冲裁剪不再"切坏"历史（只服务几秒接续，可考虑调小）
